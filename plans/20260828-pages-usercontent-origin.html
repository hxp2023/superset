Usercontent Architecture

How every byte a person or agent uploads to Superset — a published page, a screenshot on an issue, a recording in a chat, an avatar — is stored, protected, and served, for the product we're building: issues and docs, pages, and a federated chat harness.

One rule

Bytes never pass through the API — with one exception, a page's entry HTML, one text file under 3 MB that rides the publish call. The API on Vercel decides who may; Cloudflare stores and serves. Clients upload straight to storage and read straight from the edge.

One domain for untrusted content

supersetusercontent.com, cookieless by design. Pages get one origin each under pages.; uploads are served from media.; public assets from static.. Nothing user-authored ever runs on superset.sh.

One way to prove access

A ticket: a short signed statement from the API — "this page (or file) may be read until exp" — that the edge verifies with a shared secret. No cookies, no database at the edge, no API call per view.

One media model, two doors

A files table is the library; an attachments row places a file on an issue, a doc, a chat session, or a page. Access always derives from the parent. The app reads files through media. with a ticket; a page reads its own files through its own origin — same object, two doors.

Scope

What v1 ships

Video inside pages: a directory publish with <video src="demo.mp4"> plays from the page's own origin, streamed by byte range. The files and attachments layer ships with it as architecture — the files and attachments tables, presigned direct-to-R2 upload with verification on completion, the /files/<fileId> media route, the serve-time content policy — while the issue and chat attachment UI follows later. What that makes non-negotiable for v1: Range on every media path, size and type verified before a file is ready, an upload path that works from the desktop's file:// renderer, media-src for media. in the desktop renderer's CSP, expo-video on mobile, and a codec policy — browsers play H.264 MP4 and WebM reliably, and iPhone recordings are HEVC, so v1 accepts originals, the publish warns on a non-web-playable video, and the mobile composer transcodes (boilerplate AVAssetExportSession) when it moves to the files layer. decided August 30.

Vocabulary

Three things to understand first

The Worker

A Cloudflare Worker is a small function that runs at Cloudflare's edge on every request to the hostnames routed to it. There is no server to operate, it scales horizontally, and it reads R2 through a binding — an in-network call with no credentials to manage. Ours handles one request like this: hostname → page id (or the media host); look up what to serve; check the ticket if the content isn't public; read the bytes from R2; add our headers; respond. It holds no state and knows nothing about users.

The manifest

A small JSON file the API writes into R2 beside a page's bytes, at pages/<pageId>/manifest.json: the page's slug (for the sign-in redirect), its visibility, which version is shared or latest, the storage key of every version, and for each version the assets published with it and their relative paths. It is an index card. The Worker reads it to answer "what does this hostname serve, and who may see it?" without owning a database or calling the API. The API rewrites it whenever one of those facts changes — publish, visibility change, shared-version change, delete — so flipping a page's visibility is the kill switch, and an API outage never takes a page down.

{
  "v": 1,
  "pageId": "d28d7b35-813f-43a0-b3f9-9d8988dd1d58",
  "slug": "pages-on-their-own-origin-vjz0yb",
  "visibility": "org",
  "sharedVersion": null,
  "latestVersion": 2,
  "versions": {
    "1": { "key": "pages/d28d7b35-…/versions/1/index.html", "contentType": "text/html" },
    "2": {

        "app.js":        { "key": "files/2a9d…/original", "contentType": "text/javascript" }
      }
    }
  }
}

The ticket, and why the Worker has to check it

supersetusercontent.com is cookieless on purpose: that is what stops a page's script from ever touching a session. It also means the Worker has no session — no idea who is asking. So a request for anything that isn't public has to carry proof that the API already decided this reader may see it. That proof is the ticket: an HMAC-SHA256 signature over a few readable claims, signed by the API with a secret it shares with the Worker.

{ "kind": "page", "pageId": "d28d7b35-…", "version": 2, "exp": 1787954814 }   → base64url(claims).base64url(signature)
{ "kind": "file", "fileId": "8f1c…",                  "exp": 1787954814 }

The API mints one after its normal access check (session, org membership, visibility) whenever it returns a page or a file — with an expiry rounded to a window — an hour for the served alias /, a day for a pinned version or a file — so identical claims give an identical URL within the window and caches can hold what they fetched; re-minted on every listing, but the same ticket until the window turns. The Worker verifies the signature and the expiry, and that the kind and id match what's being asked for. That's all it needs: the box office checks your ID and hands you a wristband; the door only checks the wristband is real. A ticket carries no identity and grants nothing beyond the one page or file it names. Public content skips the check entirely.

Why not something off the shelf? An R2 presigned URL is the same idea signed by AWS's algorithm — but it points at Cloudflare's S3 host instead of ours, can't carry our headers or serve a page's origin, and every URL is unique so nothing caches. A JWT verified against the auth JWKS (what relay2 does) works, but puts a key fetch on the read path and makes URLs four times longer. A cookie on the media domain needs a redirect handshake. The ticket is sixty lines of WebCrypto and lets a forty-line Worker verify with zero dependencies. Two secrets are accepted during rotation so nothing in flight breaks.

Why files have two doors

The rule is who renders the reference. When the app renders an image on an issue or in a chat, it builds the tag, so it can attach a fresh ticket to the URL — those files are served from media.. When a page renders an image, the reference lives in immutable, agent-authored HTML and a ticket expires in an hour, so a ticketed media. URL baked into the page would be dead by tomorrow. Files referenced from inside a page are therefore served from the page's own origin — at their relative paths, or at /files/<id> when attached by id — authorized by the ticket in the document's own path: a private version is opened at /versions/<n>/~<ticket>/, so every relative reference resolves under that prefix and carries the ticket by construction — no cookie, and base-uri 'none' keeps a page from escaping the prefix. It works identically in Chrome, Safari, Electron's file:// top level and a WKWebView; a partitioned cookie would not, because Safari blocks third-party cookies and our web viewer is a third-party iframe. (A live check of Claude's artifacts on August 30 found the same conclusion shipped: their frame documents are capability paths with inherited relative references, served with no cookies at all — our ticketed prefix is that model plus a signature and an expiry.) Same files/<id>/original object in R2, two doors in the Worker. This is the mechanism measured in Claude's artifacts — relative _blob/{id} under the version's base path, riding __Host- ticket cookies the document set. Publishing is a directory, not a file: superset pages publish ./site/ uploads the assets straight to R2 with presigned PUTs, then publishes index.html with the manifest mapping each relative path, so <img src="img/chart.png"> and <script src="app.js"> work unchanged. A single file still publishes exactly as today. This lands in the same step as the media route. proposed

Flows

What happens, step by step

Publish a page built assets, key layout

  1. Client uploads the page's assets straight to R2 (presigned PUTs), then sends the entry HTML (≤3 MB) and the asset paths to page.publish. A single file skips the first half.
  2. API reserves the next version number, writes the bytes to pages/<pageId>/versions/<n>/index.html, records the version and its assets in Neon, then rewrites the manifest.
  3. API queues a thumbnail job; Browser Rendering loads the page through the Worker with a five-minute ticket and stores a JPEG.

View a page built

  1. Viewer asks the API for the page; the API checks visibility and returns viewUrl with a one-hour ticket (none if public).
  2. The app frames that URL in a sandboxed iframe with allow-same-origin.
  3. The Worker reads the manifest, verifies the ticket, streams the version with one CSP, and injects the comment runtime.

Upload a file proposed

  1. files.createUpload({parent, filename, contentType, sizeBytes}) — API checks the parent and the per-type size cap, inserts a pending row, returns a presigned PUT (15 min, content type signed in).
  2. Client PUTs straight to R2 with progress. The API never sees the bytes.
  3. files.complete(id) — API HEADs the object, confirms size and type, marks it ready. Pending rows older than 24 h are swept with their objects.

View a file proposed

  1. Whatever returns the parent (an issue, a chat, a doc) returns each file's URL with a ticket already attached.
  2. The Worker verifies it, reads files/<id>/original with Range, and serves with nosniff; inline only for image, video and audio, download for everything else.
  3. Public assets skip all of this: a bare, immutable URL on the CDN.
Thumbnails

How a page gets its picture

A thumbnail is a capture of exactly what a reader sees — same bytes, same headers, same policy — taken by Cloudflare Browser Rendering through the page's own origin, so there is no second rendering path to keep honest. built — assets follow with the media route.

  1. Trigger. page.publish, after the version row commits and the manifest is written, queues {pageId, version} to QStash: POST /api/pages/jobs/thumbnail, dedup id page-thumbnail-<pageId>-<n>, three retries. page.setSharedVersion queues the same job for the newly pinned version, since it may have been superseded before it was ever captured. In development the route is called directly.
  2. Guard. The job verifies the QStash signature, loads the page, and skips unless the version is the one the grid shows (sharedVersion ?? latest) — an agent that republished five times since the job was queued gets one capture. It rewrites the manifest first, so the capture never 404s on a page that exists.
  3. Capture. A five-minute, version-bound page ticket; POST /accounts/<id>/browser-rendering/screenshot with the URL https://<pageId>.pages.supersetusercontent.com/versions/<n>/?ticket=…, viewport 1280×880, JPEG quality 75, waitUntil: load with a 15 s navigation cap, 500 ms settle, bestAttempt so a slow page yields whatever rendered rather than nothing, script network requests rejected, no Cloudflare-side cache. The document response sets the same partitioned cookie a reader's would, so a page's assets load in the capture too — the thumbnail is the real page.
  4. Store. The JPEG goes to pages/<pageId>/versions/<n>/thumbnail.jpg — the same path it is served at — immutable for that version. No database column: existence is the state.
  5. Serve. /versions/<n>/thumbnail.jpg on the page origin, page ticket for private pages, bare and immutable for public. page.list returns each page's thumbnailUrl for the served version with a ticket attached; the grid's <img> shows a placeholder on 404 and picks the image up on the next refetch — typically 2–6 s after publish.
  6. Failure. A failed capture throws, QStash retries with backoff; a page that never captures shows the placeholder until its next publish. Cost is browser time only, ~3 s per capture, inside Workers Paid's included hours at our volume.

Previews of uploaded files (an image in a chat, a video on an issue) are a different thing and not stored: image sizes come from an on-the-fly transform (?width=) cached at the edge, and video posters land as a derived key next to the file — both later, each a contained addition. proposed

Devices

Caching on devices

Cache entries are keyed by the storage key the Worker names in a Superset-Storage-Key header — never by the URL, which carries a ticket that rotates — and what may be kept is the Worker's Cache-Control. Tickets are rounded to a window so URLs hold still (an hour for /, a day for a pinned version and its assets); each platform's built-in cache is sized to hold video; and desktop, where Electron can stand in front of its own session's requests, keeps everything from the user-content hosts in a store of its own with byte ranges served from disk. iOS cannot intercept a WKWebView's requests, so page media there is WebKit's cache alone, and app-rendered images go through expo-image keyed the same way. The full plan — contract, per-platform mechanism, the desktop store's schema and request flow, the spike it needs, and the alternatives set aside — is the companion document Device Content Cache (artifact). The contract and the sized built-in caches are decided; the desktop store is deferred to SUPER-2076.

Security

The boundary, in order of importance

  1. Origin isolation. User content lives on a separate registrable domain with no cookies. A page's script has the full authority of its origin and none of ours. This is the wall.
  2. One content policy for pages, identical in every viewer: default-src 'none'; inline scripts and styles allowed, plus same-origin assets published with the page; remote images, media and font files allowed; no fetch, no remote scripts or stylesheets; frame-ancestors limited to the app (and file: for the packaged desktop renderer). A second layer, never the boundary.
  3. Nothing on the media host executes. Every response carries nosniff and Content-Security-Policy: sandbox; default-src 'none'; documents that could run script (HTML, XML, SVG opened directly) are downloads. So the media host cannot execute anything even if origin isolation somehow failed.
  4. Tickets carry no identity, expire in an hour, name exactly one page or file, and can't be swapped between kinds.
  5. Referrer and robots. Referrer-Policy: no-referrer so a tokened URL never leaks through a subresource; X-Robots-Tag: noindex so nothing on the usercontent domain is crawled.
Content policy

Every type uploads; the response decides what a browser may do

Issues, docs, chat and pages will all carry arbitrary files, so there is no allowlist at write time — only per-type caps (images 25 MB · video 2 GB · audio 200 MB · other 100 MB · page entry HTML 3 MB). Safety is a property of the response: what is served inline, what is a download, and the headers every response carries. decided

Alternatives

Simpler paths we looked at, and what they cost

Vercel Private Blob for files

Client uploads with multipart and progress out of the box, signed URLs, Range — and no media route to write. Costs egress ($0.05/GB, the one line that scales with readers), URLs on Vercel's host, and a second storage vendor next to pages on R2. The files/attachments model is identical either way, so this remains a swap if "fewest moving parts this quarter" wins.

Keep pages as srcdoc

No Worker, no domain. Keeps every storage API throwing inside pages, keeps two viewers on two policies, and keeps all page blobs on one shared public origin. The spec rejected it; so did we.

Worker asks the API instead of reading a manifest

Fewer write sites, one more network hop per view, and serving depends on the API. Kept as the documented escape hatch.

Puppeteer on Vercel for thumbnails

Before any of it can ship

Prerequisites only an account owner can do. The pages spike is code-complete; none of the infrastructure is provisioned.
  1. DNS. supersetusercontent.com sits on Vercel nameservers. Move the zone to the Superset Cloudflare account, switch nameservers at Name.com, add proxied records for *.pages, pages, media, static and @, and enable Advanced Certificate Manager for the *.pages wildcard.
  2. R2. superset-private and superset-public (+ -dev twins); an S3 API token; a custom domain on the public bucket.
  3. Browser Rendering. An API token; Workers Paid for its rate limits.

  5. Site isolation. A Public Suffix List request for pages.supersetusercontent.com (a _psl TXT record plus a pull request to the list; months to reach shipped browsers, so filed now), and Origin-Agent-Cluster: ?1 from the Worker in the meantime. decided

Plugins and runtimes live elsewhere

Superset plugins follow Claude's plugin model: a plugin is a directory in git — plugin.json, skills/, commands/, agents/, hooks/, .mcp.json — listed by a marketplace repo, installed by a git fetch, with MCP servers launched by a declared command. Nothing in that needs a bucket, and nothing in this document applies to it: plugins are our code executing on people's machines, so the concern is integrity, the opposite of the isolation the usercontent origin exists for. proposed

  • Plugin directories: git, tagged versions, never bundled into the desktop app — they update on their own cadence and Claude/Codex users without the app need them from the marketplace.
  • A binary runtime: a release. Start on GitHub Releases, where desktop, host-service and the CLI already ship in lockstep: CI publishes per-platform assets with checksums on the tag, and a small launcher named in .mcp.json fetches and verifies the runtime into ~/.superset/runtimes/<name>/<version>/ on first use. If it is one shared runtime, ship one binary per platform in total and let plugins stay scripts.
  • When a marketplace carries many or private binaries: a public R2 bucket on releases.superset.sh reusing the patterns here — immutable versioned keys, a CI-written manifest, CDN, zero egress — and the ticket Worker as-is for private ones. Never the files model, never the usercontent domain.
