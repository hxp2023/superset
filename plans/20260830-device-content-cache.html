Companion to Usercontent Architecture

Device Content Cache

How a page's images and video, an attachment on an issue, and a thumbnail in the grid get onto a person's device once and stay there — on desktop, on iOS, and on the web — without a second copy of the access rules.

One contract

A cache entry is keyed by the storage key — files/<fileId>/original, pages/<pageId>/versions/3/thumbnail.jpg — never by the URL, because the URL carries a ticket that rotates. What may be kept, and for how long, is the Worker's Cache-Control. No client carries its own idea of what is safe to keep.

Three layers, cheapest first

The server makes URLs cacheable at all. Each platform's built-in cache is then sized so it actually holds video. Only desktop, where Chromium lets the app stand in front of requests, gets a store of its own for offline and for anything larger than a browser cache will hold.

Documents pass through; bytes get cached

A page's HTML is small and carries the access decision — the sign-in redirect, the served-version choice — so it is always fetched. Assets, attachments and thumbnails are the bytes that cost, and they are immutable, so they are what gets kept.

Platforms differ, the contract doesn't

Electron can intercept its own session's requests; a WKWebView cannot. So desktop runs a store, iOS relies on WebKit plus expo-image keyed the same way, and the web is the browser cache. Same keys, same policy, three mechanisms.

Why

Why "the browser has a cache" isn't the whole answer

Money is not the problem: R2 egress is free and a Worker request is $0.30 per million, so re-serving a 50 MB video costs us nothing measurable. The viewer's bandwidth and the load time are the problem, and the built-in HTTP caches lose large files for three reasons that compound:

  • Entry size cap. Chromium refuses to store a single entry larger than a fraction (about an eighth) of its cache's maximum. With the default cache of a few hundred MB, anything past a few tens of MB is never cached at all. WebKit has its own limits, and neither is documented as a contract.
  • Eviction pressure. Everything else the app loads competes in the same LRU — on desktop that includes the in-app browser pane. A big entry is the first casualty.
  • URL rotation. The ticket is in the URL, so the URL is the cache key, and today every list mints a new ticket. Even with rounded tickets, a private asset's URL changes every window, and the browser starts over.

The first two are sizing; the third is ours to fix, and fixing it is what makes the other two worth doing.

Contract

The contract every platform implements

Key: the storage key

The Worker answers every content response with Superset-Storage-Key, the R2 key it read: files/8f1c…/original for an asset or attachment, pages/<pageId>/versions/3/thumbnail.jpg for a capture. The API returns the same value as storageKey beside every URL it hands out (page.list thumbnails, attachment listings), so a client that builds an <img> itself can key its cache without parsing anything. A file reused across two versions of a page — or attached to two issues — is one entry. built — the Worker sends the header, and page.list/pull return storageKey.

Policy: the Worker's Cache-Control

Clients keep exactly what the response says they may. no-store and no-cache are never stored; immutable is kept until evicted. Nothing on a device decides cacheability on its own.

Tickets that hold still

A ticket's expiry is rounded to a window boundary: exp = ceil(now ÷ window) × window + window. Identical claims produce an identical signature, so within a window every mint yields the same URL, and a ticket is always good for at least one full window (never the one-minute sliver a plain ceiling would give at 23:59). The served alias / uses an hour; a pinned /versions/<n>/ is immutable, so its ticket — and every asset URL under it, which inherits the ticket from the document's path — uses a day. built — with the thumbnail ticket version-bound so it turns daily.

The policy call. A day-long window means someone whose access was revoked can keep reloading a pinned version, and its assets, for up to a day. An hour means every private asset re-downloads hourly on every platform, including the ones that can't intercept. The day is the recommendation; it is one constant. open

Layer 3

The desktop content store

Deferred on August 30. Pages have no assets until directory publish lands and no video exists in the product yet, so the store optimises for content that isn't there; the server contract and the sized built-in caches above carry every platform until it is. Tracked as SUPER-2076. Trigger: video attachments ship on desktop and reload cost shows in numbers, or offline reading becomes a goal. When it is picked up, the design is the one below, with the page viewer on its own session (decided over the session-wide intercept, so nothing sits in front of the browser pane and frame-ancestors file: stops mattering). deferred

Electron lets the main process answer requests for its own session, so desktop can keep everything from the user-content hosts on disk, keyed by storage key, with a cap it controls — and serve a cached video's byte ranges from the file.

Where it lives

  • Bytes: ~/.superset/content-cache/<sha256 of the storage key>, one file per entry, written to a temporary name and renamed on completion so a crash never leaves a half entry indexed. The app's own root, like everything else it stores, not Electron's userData.
  • Index: a content_cache table in @superset/local-db (drizzle migration, same as screenshots), because entity-keyed data of unbounded cardinality belongs in SQLite. Two levels: a canonical URL (host + path with the ticket segment removed) points at a storage key; the storage key points at the bytes. Two versions referencing one file, or one thumbnail listed under a hundred tickets, are one set of bytes.

How a request reaches it

session.fromPartition("persist:superset").protocol.handle("https", handler) — on the window's partition, as the icon and font handlers already are. The handler's first line is the fast path: any host that is not *.pages.supersetusercontent.com, media.supersetusercontent.com or static.supersetusercontent.com is returned as net.fetch(request, { bypassCustomProtocolHandlers: true }), Electron's documented way of forwarding an intercepted request to the built-in handler. For our hosts:

RequestWhat happens
Sec-Fetch-Dest: document or iframePass through. Documents carry the sign-in redirect and the served-version choice, and are small.
Hit (canonical URL known, entry present)Serve from disk with the stored headers, 200 or 206 for a Range; touch last_accessed_at. No ticket check — the bytes are already on this machine, as with any browser cache.
Miss, no RangeFetch upstream with the ticket in the URL. If 200 and the policy allows storing and Content-Length is under the per-entry cap, tee the body: one branch streams to the renderer, one to the temporary file; on completion, index under the Superset-Storage-Key the response named.
Miss, with Range (a <video> starting up)Forward the ranged request as is — the viewer plays from the network the first time — and start one background full download of the key, deduplicated, so the next play is from disk.
Upstream 302, 404, or no-storePass through untouched.

Bounds and lifecycle

  • Cap: a contentCacheMaxBytes setting in the single-row settings table, default 2 GiB, range 512 MiB – 20 GiB, shown under Settings → Storage with the bytes in use and a Clear button. Per-entry cap 512 MiB; larger responses pass through.
  • Eviction: LRU on last_accessed_at, run after any write that crosses the cap and once at boot, never touching an entry mid-write. Index rows whose file is missing are dropped on the boot sweep.
  • Sign-out: auth.signOut clears the store and calls ses.clearCache(). Today nothing clears the session cache on sign-out; this fixes that too.
  • Telemetry: hit, miss and evict counters in the main-process log, no Sentry breadcrumbs.

What the spike has to prove first

Half a day, before the store is written. The intercept sits in front of every request in the session, including the in-app browser pane, so the unknowns are about not breaking that:

  1. Redirects in the browser pane. net.fetch follows redirects itself, and Electron warns the returned Response's url is wrong. A navigation to a site that redirects must still land on the final URL in the address bar. Try redirect: "manual" so Chromium performs the redirect; if the pane misbehaves, use the fallback below.
  2. Sec-Fetch-Dest is present on the Request the handler receives, so documents can be told from media without a resource-type API.
  3. Overhead on a heavy page in the browser pane is not noticeable; the fast path is one host comparison and a forwarded fetch.
Fallback. Render the page viewer in a <webview partition="persist:superset-pages"> and register the handler on that session alone, leaving the app session and the browser pane untouched. It costs an IPC relay for the comment bridge (the host and the page talk over postMessage today) — the same fallback the parent doc already names for the unverified frame-ancestors file: assumption, so it would settle two unknowns at once.
iOS

Mobile: what WebKit allows, and what we build around it

There is no page viewer on mobile yet — the only WebView in the app is the terminal, loading an HTML string — so this is the viewer's specification as much as its cache. The viewer and ContentImage are decided for the release (August 30); expo-video waits for the attachments UI, since video inside a page plays natively in the WebView.

The page viewer

A react-native-webview loading viewUrl top-level: source={{ uri }}, never HTML. The page's origin is then first-party inside the WebView, so its storage works and its CSP applies exactly as on the web. Props: allowsInlineMediaPlayback, mediaPlaybackRequiresUserAction={false}, setSupportMultipleWindows={false}, onShouldStartLoadWithRequest that keeps navigation on the page's own origin and hands anything else to Safari, no injectedJavaScript, no sharedCookiesEnabled, and the default cacheEnabled. Keep the loaded URL for the ticket's window (react-query staleTime), so returning to a page reuses the URL — and the cache — instead of minting a fresh one.

What iOS does not allow

WKWebView has no resource-level interception for https; react-native-webview's onShouldStartLoadWithRequest sees navigations, not images or video. So page-internal media on iOS is cached by WebKit alone, under WebKit's limits, refreshed at most once per ticket window. That is the accepted ceiling for the release. The one route past it — a Service Worker registered by our runtime script, enabled through App-Bound Domains — needs WKAppBoundDomains in the plist, the com.apple.developer.WebKit entitlement, gives each page origin its own quota with nothing shared between pages, and downgrades every other WebView in the app once the key exists. Not for now. open

App-rendered attachments

  • Images: a ContentImage component over expo-image that takes { url, storageKey } and sets cacheKey: storageKey, cachePolicy: "disk"; Image.configureCache({ maxDiskSize }) at boot. Every remote image in the app — attachments, thumbnails, avatars — goes through it; today none set a cache key, so a rotated URL is a fresh download.
  • Video: add expo-video when there is a video to play; useCaching: true, cache size set once at boot, source URL from the API. Its cache is URL-keyed, which the day-stable ticket makes workable.
  • Other files (a PDF, a download): expo-file-system's File.downloadFileAsync into Paths.cache/content/<storage key>, with a small index and LRU cap. Only once such a screen exists.
  • Sign-out: Image.clearDiskCache(), Video.clearVideoCacheAsync(), remove Paths.cache/content.
Web

Web: nothing to build

The browser's HTTP cache is the contract. With rounded tickets and the headers above, an asset or thumbnail is fetched once per window per browser; a very large video re-downloads past the browser's own entry cap, which is the browser's decision to make.

Server

What this asks of the Worker and the API

  • Superset-Storage-Key on every content response from the Worker; storageKey beside every content URL the API returns.
  • Ticket expiry rounded to a window: an hour for /, a day for /versions/<n>/ and for file tickets.
  • The Cache-Control table above, with Accept-Ranges: bytes and Range honoured on /files/ and on page assets.
  • Nothing else — no cache API, no invalidation protocol. Immutable keys mean there is nothing to invalidate; a new version or a replaced file is a new key.
